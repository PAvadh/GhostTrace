# data/amlsim — provenance (READ THIS FIRST)

## What is in this folder today

| File | What it really is | Official AMLSim output? |
|---|---|---|
| `transactions_sample.csv` | 12 hand-written rows in the AMLSim-native *column layout* (`tran_id, orig_acct, bene_acct, tx_type, base_amt, tran_timestamp, is_sar`). Written by the GhostTrace project as a **test fixture**. | **No.** Not generated by IBM AMLSim. |
| `HI-Small_Sample.csv` | 25 hand-written rows in the column layout of the *IBM IT-AML / Kaggle "HI-Small"* dataset (`Timestamp, From Bank, Account, …, Is Laundering`). Written by the GhostTrace project as a **test fixture**. | **No.** Not AMLSim, and not from the Kaggle dataset either. IT-AML is a *different* IBM generator from AMLSim. |

These two files exist so the adapter and dashboard tests can run offline. They contain **no real
AMLSim data**, their labels are the fixture author's own, and nothing computed from them may be
described as an AMLSim result.

Status: **not retrieved.** The project's build environment had no network access and the

### How to add it (offline-capable afterwards)

1. Open the wiki page above, follow its Dropbox link, and download `100vertices-10Kedges`
   (7-Zip). Use only that one small archive, not the whole folder.
2. Extract it and copy the CSVs into
   `data/amlsim/official/100vertices-10Kedges/` (keep the original file names; the
   transaction file is expected to be `transactions.csv`).
3. Inspect the header yourself. The wiki documents this schema for `transactions.csv`:
   `tran_id, orig_acct, bene_acct, tx_type, base_amt, tran_timestamp, is_sar, alert_id`
   (`tran_timestamp` = integer simulation step; `alert_id` = -1 when not in an alert).
4. Run the integration test, which is skipped until the file exists:
   `python -m pytest tests/test_amlsim_official_sample.py -q`
5. In the dashboard choose *IBM AMLSim Dataset* -> *Select pre-placed file* and pick the
   transaction CSV (copy it up to `data/amlsim/` if the picker only lists that folder).

### Label caveat (must be resolved by inspecting the files)

The wiki says `is_sar` marks SAR transactions and `alert_id >= 0` marks transactions that belong
to an alert pattern, and that an alert can be a SAR *or a false alert*. Whether the single
fan_in pattern in this sample is a true SAR is not known until the files are read. Do not
treat the labels as "fraud" ground truth, and do not compute precision/recall, until that has
been checked and the unit of evaluation (transaction vs account vs pattern) has been fixed.
